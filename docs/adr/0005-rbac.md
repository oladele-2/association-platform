# ADR 0005: Role-based access control (RBAC)

- **Status:** Accepted
- **Date:** 2026-08-04
- **Deciders:** Product / Architecture review
- **Related:** ADR 0001, Functional Specification §16

## Context

Associations need named roles (State Administrator, Treasurer, Financial Secretary, Secretariat Staff, Institution Administrator, Member, etc.) with different capabilities. Hard-coding role *names* in business logic would freeze product language to NMA and block other association types.

Platform Operators (Ajir staff) need a separate privilege plane from tenant admins.

## Decision

Use **permission-based RBAC**:

1. Global `permissions` catalog (stable string keys, e.g. `payments.verify`, `cms.publish`, `members.write`)
2. Per-tenant `roles` with labels/keys orgs can customize; system-seeded templates on provision
3. `role_permissions` grants permissions to roles
4. `user_roles` assigns roles to users, optionally scoped (`organization` | `institution` | `committee` + `scope_id`)
5. Application authorization checks **permissions** (and resource scope), never `if (role === 'Treasurer')`
6. **Platform RBAC** is separate (`platform_users` / `platform_roles`) and uses platform JWT + RLS bypass flag — not tenant roles
7. Presentation layer: Nest guards; business rules still live in domain/application

Institution admins are modeled as scoped role assignments and/or `institution_admins`, enforced in application services.

## Consequences

### Positive

- Same product serves medical, legal, alumni, NGO tenants with different role *labels*
- Granular least privilege; finance vs CMS separation
- Audit-friendly (permission + actor on sensitive actions)

### Negative / risks

- Up-front permission seed design required; renaming keys later is breaking
- Scoped roles add complexity — keep committee scope shallow until Phase 2 needs it
- UI must hide unauthorized nav and block deep links

### Follow-ups

- Milestone 4: seed permission catalog + default role templates on org provision
- Map Functional Spec screens to permission keys in seed data
- Optional Phase 2: MFA for users holding finance permissions
