# ADR 0006: Neon as PostgreSQL host

- **Status:** Accepted
- **Date:** 2026-08-04
- **Deciders:** Product / Architecture
- **Related:** ADR 0001, ADR 0002

## Context

The platform needs managed PostgreSQL with backups, SSL, and low ops burden. DigitalOcean Managed Postgres was the earlier default in the high-level plan; the team prefers **Neon** for developer experience (branching, serverless scaling, Prisma-friendly pooling).

## Decision

Use **Neon** as the primary PostgreSQL provider for development, staging, and production (unless a later constraint forces otherwise).

- Application `DATABASE_URL`: Neon **pooled** connection (`-pooler` host, `sslmode=require`)
- Migrations `DATABASE_URL_UNPOOLED` / Prisma `directUrl`: Neon **direct** connection
- Postgres 16+; enable extensions used by schema (`pgcrypto`, `citext`) on Neon
- Local Docker Postgres remains optional for offline work; Neon is the team default

Row Level Security and tenancy decisions in ADR 0001 are unchanged.

## Consequences

### Positive

- Fast provisioning; database branching for preview/migrate workflows
- No Droplet-local Postgres for default path
- Aligns with Prisma migrate + serverless drivers if adopted later

### Negative / risks

- Must use `directUrl` for migrations (pooler is not suitable for migrate)
- RLS + connection pooling discipline remains critical (`SET LOCAL` in transactions)
- Region choice affects latency from DigitalOcean API hosts

### Follow-ups

- Wire Prisma `directUrl` in Milestone 2
- Document Neon project/branch naming for staging vs production
- Create non-owner DB role for the app once RLS ships
